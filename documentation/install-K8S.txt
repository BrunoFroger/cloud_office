cree moi un script d'installation kubernetes 

Voici un script complet en Bash pour installer Kubernetes (kubeadm) sur une distribution basée sur Ubuntu (22.04 / 24.04).
Ce script configure les prérequis systèmes, installe le moteur de conteneur CRI-O, puis installe les outils Kubernetes (kubelet, kubeadm, kubectl).
📄 Script d'installation (install-k8s.sh)
bash
#!/bin/bash

# Quitter immédiatement si une commande échoue
set -e

echo "=== 1. Désactivation du Swap ==="
sudo swapoff -a
sudo sed -i '/ swap / s/^\(.*\)$/#\1/g' /etc/fstab

echo "=== 2. Configuration des modules du noyau pour le réseau ==="
cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF

sudo modprobe overlay
sudo modprobe br_netfilter

echo "=== 3. Configuration des paramètres Sysctl (Réseau) ==="
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF

sudo sysctl --system

echo "=== 4. Installation des dépendances de base ==="
sudo apt-get update
sudo apt-get install -y apt-transport-https ca-certificates curl gnupg

echo "=== 5. Installation du runtime de conteneur (CRI-O) ==="
# Définition de la version stable actuelle
CRIO_VERSION=v1.30

# Ajout du dépôt CRI-O
sudo mkdir -p /etc/apt/keyrings
curl -fsSL https://download.opensuse.org/repositories/isv:/cri-o:/stable:/${CRIO_VERSION}/deb/Release.key | sudo gpg --dearmor -o /etc/apt/keyrings/cri-o-apt-keyring.gpg
echo "deb [signed-by=/etc/apt/keyrings/cri-o-apt-keyring.gpg] https://k8s.io /" | sudo tee /etc/apt/sources.list.d/cri-o.list

sudo apt-get update
sudo apt-get install -y cri-o
sudo systemctl daemon-reload
sudo systemctl enable cri-o --now

echo "=== 6. Installation de Kubeadm, Kubelet et Kubectl ==="
# Ajout du dépôt Kubernetes (Dépôt officiel communautaire pkgs.k8s.io)
K8S_VERSION=v1.30
curl -fsSL https://pkgs.k8s.io/core:/stable:/${K8S_VERSION}/deb/Release.key | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo "deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://k8s.io /" | sudo tee /etc/apt/sources.list.d/kubernetes.list

sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl

sudo systemctl enable kubelet --now

echo "=========================================================="
echo " Installation terminée avec succès !"
echo " Prochaines étapes :"
echo " - Sur le nœud Master : sudo kubeadm init --pod-network-cidr=10.244.0.0/16"
echo "=========================================================="
Utilisez le code avec précaution.

Voici le script et les étapes pour initialiser votre nœud Master (Control Plane) et configurer l'accès à votre cluster.
Pour cet exemple, nous allons installer Cilium comme plugin réseau (CNI), car il s'agit du standard moderne le plus performant, mais vous pouvez aussi utiliser Calico.
📄 Script d'initialisation (init-master.sh)
Exécutez ce script uniquement sur la machine qui servira de Master.
bash
#!/bin/bash
set -e

# Adresse IP privée de ce nœud Master (détection automatique)
MASTER_IP=$(hostname -I | awk '{print $1}')

echo "=== 1. Initialisation du cluster avec Kubeadm ==="
# Nous définissons le CIDR pour les Pods (requis par la plupart des réseaux comme Cilium/Calico)
sudo kubeadm init \
  --apiserver-advertise-address=$MASTER_IP \
  --pod-network-cidr=10.244.0.0/16

echo "=== 2. Configuration de Kubectl pour votre utilisateur actif ==="
mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

echo "=== 3. Installation du plugin réseau (Cilium CNI) ==="
# Récupération de la dernière version stable de Cilium CLI
CILIUM_CLI_VERSION=$(curl -s https://githubusercontent.com)
CLI_ARCH=amd64
if [ "$(uname -m)" = "aarch64" ]; then CLI_ARCH=arm64; fi

curl -L --fail --remote-name-all https://github.com{CILIUM_CLI_VERSION}/cilium-linux-${CLI_ARCH}.tar.gz{,.sha256sum}
sha256sum --check cilium-linux-${CLI_ARCH}.tar.gz.sha256sum
sudo tar xzvfC cilium-linux-${CLI_ARCH}.tar.gz /usr/local/bin
rm cilium-linux-${CLI_ARCH}.tar.gz{,.sha256sum}

# Déploiement de Cilium dans le cluster
cilium install

echo "=========================================================="
echo " Le nœud Master est initialisé avec succès !"
echo " Vérifiez l'état avec : kubectl get nodes"
echo "=========================================================="
Utilisez le code avec précaution.

donne moi les instruction pour ouvrir un cluster kubernetes a internet derriere une livebox

Pour ouvrir les services de votre cluster Kubernetes vers Internet derrière une Orange Livebox, vous devez associer l'adressage interne du cluster à une redirection de port (NAT/PAT) sur votre box.
Cependant, la Livebox a une limitation technique majeure : son interface graphique refuse de créer une règle NAT vers une adresse IP virtuelle si celle-ci n'est pas directement associée à une adresse MAC physique connue. [1]
Voici la procédure pas-à-pas pour réussir cette configuration de manière propre et sécurisée.

Étape 1 : Configurer un Ingress Controller ou un LoadBalancer interne
N'essayez pas d'ouvrir chaque pod individuellement. Vous devez centraliser le trafic entrant du cluster.
    1. Option Recommandée (Ingress Nginx/Traefik) : Déployez un Ingress Controller. Associez-le à un service configuré en NodePort (par exemple, le port 32080 pour le HTTP et 32443 pour le HTTPS). Le trafic envoyé sur ces ports de n'importe quel Node sera redirigé vers vos applications. [1]
    2. Option LoadBalancer (MetalLB) : Si vous utilisez un outil comme MetalLB, attribuez une IP fixe à votre LoadBalancer (ex: 192.168.1.250), située en dehors de la plage DHCP de votre Livebox pour éviter les conflits. [1]
Étape 2 : Fixer l'adresse IP de votre Node (Machine physique ou VM)
Si vous utilisez la méthode NodePort (recommandée avec une Livebox), assurez-vous que la machine qui héberge ce Node garde toujours la même IP privée.
    1. Connectez-vous à l'interface de votre Livebox (généralement http://192.168.1.1).
    2. Allez dans Paramètres avancés > Réseau > DHCP.
    3. Dans la section Baux DHCP statiques, ajoutez votre équipement/Node Kubernetes pour lui attribuer définitivement son IP actuelle (ex: 192.168.1.50). [1]
Étape 3 : Configurer la redirection de port (NAT/PAT) sur la Livebox
C'est ici que vous exposez les ports standards du web (80 et 443) vers votre cluster. [1]
    1. Dans l'interface Livebox, allez dans Paramètres avancés > Réseau > NAT/PAT. [1]
    2. Créez une nouvelle règle pour le trafic HTTP :
        ◦ Application/Service : HTTP
        ◦ Port interne : Le port de votre NodePort (ex: 32080) ou 80 si vous redirigez vers l'IP d'un LoadBalancer MetalLB.
        ◦ Port externe : 80
        ◦ Protocole : TCP
        ◦ Équipement : Sélectionnez le nom de votre Node Kubernetes dans la liste déroulante. [1]
    3. Créez une seconde règle pour le trafic HTTPS :
        ◦ Application/Service : HTTPS
        ◦ Port interne : Le port de votre NodePort (ex: 32443) ou 443.
        ◦ Port externe : 443
        ◦ Protocole : TCP
        ◦ Équipement : Sélectionnez le même Node.
💡 Astuce de contournement (si vous utilisez MetalLB) : L'interface Livebox bloque parfois la sélection d'une IP virtuelle MetalLB. Pour contourner cela, vous pouvez utiliser l'inspecteur de votre navigateur web (F12) sur la page NAT/PAT de la Livebox, modifier manuellement le code HTML de la liste déroulante (<select>) pour y injecter la valeur de l'IP virtuelle de votre LoadBalancer, puis valider le formulaire. [1]
Étape 4 : Gérer l'IP publique dynamique (DDNS)
Les Livebox grand public changent régulièrement d'IP publique. Pour que votre cluster reste joignable, vous devez lier votre box à un nom de domaine :
    1. Dans la Livebox, allez dans Paramètres avancés > Réseau > DynDNS (ou DDNS).
    2. Configurez un fournisseur de service (comme No-IP, DynDNS, ou DuckDNS).
    3. La Livebox mettra automatiquement à jour votre nom de domaine (ex: moncluster.ddns.net) dès que votre IP publique changera.

⚠️ Recommandation de Sécurité Importante
N'exposez jamais directement le port de l'API Server de Kubernetes (6443) à Internet via la Livebox. L'exposer publiquement présente un risque majeur d'attaques par force brute ou d'exploitation de vulnérabilités. Si vous avez besoin d'administrer votre cluster à distance avec kubectl :
    • Utilisez plutôt un serveur VPN (comme WireGuard ou OpenVPN) hébergé sur votre réseau local.
    • Connectez-vous au VPN depuis l'extérieur, puis utilisez vos commandes kubectl comme si vous étiez à la maison.

configurer un ingress controleur pour centraliser le trafic entrant

Pour centraliser le trafic entrant, nous allons installer l'Ingress Controller NGINX (le plus populaire et robuste) et le configurer pour qu'il s'adapte aux contraintes de votre Livebox en utilisant le mode NodePort.
Voici le guide pas à pas avec les fichiers de configuration nécessaires.

Étape 1 : Installer l'Ingress Controller NGINX
La méthode la plus simple et standard consiste à utiliser le manifeste officiel fourni par la communauté Kubernetes.
Exécutez cette commande sur votre machine de contrôle (master node) :
bash
kubectl apply -f https://githubusercontent.com
Utilisez le code avec précaution.
(Note : Cette version "baremetal" est spécialement conçue pour les clusters hors cloud public, parfaits pour un usage domestique derrière une box).
Étape 2 : Fixer les ports NodePort pour la Livebox
Par défaut, Kubernetes attribue des ports aléatoires (entre 30000 et 32767) au service NGINX. Pour faciliter la configuration NAT/PAT dans votre Livebox, nous allons forcer l'utilisation de ports fixes (par exemple : 32080 pour le HTTP et 32443 pour le HTTPS).
    1. Ouvrez le service NGINX en mode édition :
       bash
       kubectl edit service ingress-nginx-controller -n ingress-nginx
       Utilisez le code avec précaution.
    2. Cherchez la section spec.ports et modifiez-la pour ajouter les champs nodePort comme ci-dessous :
yaml
spec:
  type: NodePort
  ports:
    - name: http
      port: 80
      protocol: TCP
      targetPort: http
      nodePort: 32080  # Port fixe pour le trafic HTTP
    - name: https
      port: 443
      protocol: TCP
      targetPort: https
      nodePort: 32443  # Port fixe pour le trafic HTTPS
Utilisez le code avec précaution.
    3. Enregistrez et quittez (si vous utilisez Nano : Ctrl+O puis Ctrl+X, si vous utilisez Vi : :wq).
C'est vers l'adresse IP de votre Node et ces ports (32080 / 32443) que vous devez diriger les règles NAT/PAT de votre Livebox (Étape 3 du message précédent).
Étape 3 : Créer une application de test
Pour vérifier que tout fonctionne, créons un déploiement simple (une application web "web-custom") et son service interne associé.
Créez un fichier nommé app-test.yaml :
yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  labels:
    app: web-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: nginx
        image: nginxdemos/hello:plain
        ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  ports:
  - port: 80
    targetPort: 80
    protocol: TCP
  selector:
    app: web-app
Utilisez le code avec précaution.
Appliquez le fichier : kubectl apply -f app-test.yaml
Étape 4 : Créer la ressource Ingress (Le routeur)
C'est ici que vous définissez la règle de routage : "Si un visiteur arrive avec le nom de domaine X, envoyez-le vers le service Y".
Créez un fichier nommé ingress-routing.yaml (remplacez moncluster.ddns.net par votre vrai nom de domaine DynDNS) :
yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main-ingress
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "false" # À passer sur "true" une fois SSL configuré
spec:
  ingressClassName: nginx
  rules:
  - host: moncluster.ddns.net  # Votre nom de domaine pointant sur la Livebox
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service # Redirige vers notre application de test
            port:
              number: 80
Utilisez le code avec précaution.
Appliquez le fichier : kubectl apply -f ingress-routing.yaml

Étape 5 : Tester la configuration
Pour valider que l'Ingress fait bien son travail en local avant de tester depuis Internet :
    1. Identifiez l'IP de votre Node Kubernetes (ex: 192.168.1.50).
    2. Exécutez une commande curl en simulant l'en-tête de votre nom de domaine :
       bash
       curl -H "Host: moncluster.ddns.net" http://192.168.1.50:32080
       Utilisez le code avec précaution.
Si vous obtenez une réponse textuelle NGINX ("Server Name", "Server Address"...), votre Ingress Controller fonctionne parfaitement ! Une fois les ports ouverts sur votre Livebox, votre application sera accessible depuis le monde entier.

configurer cert-manager avec let's encrypt pour kubernetes
Pour sécuriser votre cluster Kubernetes avec des certificats SSL/TLS gratuits et renouvelés automatiquement, nous allons installer Cert-Manager et le lier à Let's Encrypt.
Étant donné que vous êtes derrière une Livebox avec une IP publique qui peut changer, nous allons utiliser le protocole de validation HTTP-01. Let's Encrypt viendra interroger votre domaine sur le port 80 pour vérifier que vous en êtes bien le propriétaire.

Étape 1 : Installer Cert-Manager
Exécutez la commande suivante pour déployer Cert-Manager (les CRD, les contrôleurs et le webhook) dans votre cluster :
bash
kubectl apply -f https://github.com
Utilisez le code avec précaution.
(Note : Attendez environ 1 à 2 minutes que tous les pods soient dans l'état Running dans le namespace cert-manager en vérifiant avec kubectl get pods -n cert-manager).
Étape 2 : Créer le ClusterIssuer Let's Encrypt
Le ClusterIssuer est la ressource globale qui indique à Cert-Manager comment communiquer avec Let's Encrypt pour demander des certificats.
Créez un fichier nommé letsencrypt-issuer.yaml. Important : Remplacez votre-email@exemple.com par une adresse email valide (elle sert à recevoir les alertes d'expiration si le renouvellement automatique échoue).
yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    # L'URL de l'API de production de Let's Encrypt
    server: https://letsencrypt.org
    email: votre-email@exemple.com
    # Clé privée Kubernetes utilisée pour stocker votre compte ACME
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    # Configuration du défi (challenge) HTTP-01
    solvers:
    - http01:
        ingress:
          ingressClassName: nginx
Utilisez le code avec précaution.
Appliquez le fichier :
bash
kubectl apply -f letsencrypt-issuer.yaml
Utilisez le code avec précaution.
Étape 3 : Mettre à jour votre Ingress pour activer le HTTPS
Maintenant, nous allons modifier l'Ingress créé à l'étape précédente pour lui demander d'utiliser notre ClusterIssuer et de chiffrer le trafic. Cert-Manager va intercepter cette configuration, valider le domaine auprès de Let's Encrypt et générer le certificat TLS.
Créez ou modifiez votre fichier ingress-routing.yaml :
yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main-ingress
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod" # Indique à cert-manager d'agir
    nginx.ingress.kubernetes.io/ssl-redirect: "true"   # Force la redirection HTTP -> HTTPS
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - moncluster.ddns.net  # Votre nom de domaine DynDNS
    secretName: moncluster-tls-cert # Le secret où sera stocké le certificat SSL
  rules:
  - host: moncluster.ddns.net
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
Utilisez le code avec précaution.
Appliquez la nouvelle configuration :
bash
kubectl apply -f ingress-routing.yaml
Utilisez le code avec précaution.

Étape 4 : Suivre et vérifier la génération du certificat
Le processus de validation avec Let's Encrypt prend généralement entre 30 secondes et 3 minutes. Vous pouvez suivre l'avancement avec les commandes suivantes :
    1. Vérifier l'état du certificat :
       bash
       kubectl get certificate
       Utilisez le code avec précaution.
       Attendez que la colonne READY passe à True.
    2. En cas de problème (si READY reste à False), inspectez le challenge :
       bash
       kubectl describe challenge
       Utilisez le code avec précaution.
       Cela vous indiquera si Let's Encrypt ne parvient pas à joindre votre Livebox sur le port 80.
Une fois le certificat valide, vous pourrez vous rendre sur https://ddns.net depuis votre navigateur à l'extérieur de votre réseau : le cadenas vert/sécurisé sera activé, et Cert-Manager s'occupera de le renouveller automatiquement tous les 3 mois.
Si la validation échoue, cela vient souvent d'un problème de route. Souhaitez-vous que l'on vérifie ensemble le statut de votre règle NAT/PAT sur la Livebox pour le port 80 ou préférez-vous voir comment ajouter plusieurs sous-domaines sur ce même certificat ?

Voici un script Bash complet et prêt à l'emploi pour automatiser la création d'un utilisateur, de son certificat SSL/TLS et de ses accès RBAC (Role-Based Access Control) sur votre cluster Kubernetes.
Dans Kubernetes, les utilisateurs normaux sont gérés à l'externe (via des certificats ou un OIDC). Ce script génère une clé privée, une demande de signature de certificat (CSR), la soumet à Kubernetes, l'approuve, puis génère un fichier kubeconfig prêt à être envoyé à votre utilisateur.
Script Bash : create-k8s-user.sh
bash
#!/bin/bash

# Quitter immédiatement si une commande échoue
set -e

# Vérification des arguments
if [ "$#" -ne 3 ]; then
    echo "Usage: $0 <nom_utilisateur> <namespace> <role: cluster-admin|admin|edit|view>"
    echo "Exemple: $0 jean-dupont developpement view"
    exit 1
fi

USER_NAME=$1
NAMESPACE=$2
ROLE=$3
USER_DIR="./k8s-user-${USER_NAME}"

echo "🚀 Début de la création de l'utilisateur '${USER_NAME}'..."

# 1. Création d'un répertoire de travail isolé
mkdir -p "${USER_DIR}"
cd "${USER_DIR}"

# 2. Génération de la clé privée et du CSR (Certificate Signing Request)
echo "🔑 Génération de la clé privée et du CSR..."
openssl genrsa -out "${USER_NAME}.key" 2048
openssl req -new -key "${USER_NAME}.key" -out "${USER_NAME}.csr" -subj "/CN=${USER_NAME}/O=dev-group"

# 3. Envoi du CSR à l'API Kubernetes
echo "📝 Envoi de la demande de certificat (CSR) à Kubernetes..."
cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: ${USER_NAME}-csr
spec:
  request: $(cat "${USER_NAME}.csr" | base64 | tr -d '\n')
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 864000 # Valide pour 10 jours (Ajustable)
  usages:
  - client auth
EOF

# 4. Approbation du certificat par l'administrateur
echo "✅ Approbation du certificat..."
kubectl certificate approve "${USER_NAME}-csr"

# 5. Extraction du certificat signé
echo "📥 Récupération du certificat signé..."
# On attend que le certificat soit généré
until kubectl get csr "${USER_NAME}-csr" -o jsonpath='{.status.certificate}' &> /dev/null; do
    echo "Attente de la signature du certificat..."
    sleep 2
done
kubectl get csr "${USER_NAME}-csr" -o jsonpath='{.status.certificate}' | base64 -d > "${USER_NAME}.crt"

# 6. Configuration des droits d'accès (RBAC RoleBinding)
echo "🔒 Configuration des permissions (RBAC) dans le namespace '${NAMESPACE}'..."
cat <<EOF | kubectl apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: ${USER_NAME}-binding
  namespace: ${NAMESPACE}
subjects:
- kind: User
  name: ${USER_NAME}
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: ${ROLE}
  apiGroup: rbac.authorization.k8s.io
EOF

# 7. Récupération des données du cluster actuel pour le fichier kubeconfig
CLUSTER_NAME=$(kubectl config view --minify -o jsonpath='{.clusters[0].name}')
CLUSTER_SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')
CLUSTER_CA=$(kubectl config view --minify --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}')

# 8. Génération du fichier kubeconfig pour l'utilisateur
echo "⚙️ Génération du fichier kubeconfig..."
cat <<EOF > "${USER_NAME}-kubeconfig.yaml"
apiVersion: v1
kind: Config
preferences: {}
clusters:
- cluster:
    certificate-authority-data: ${CLUSTER_CA}
    server: ${CLUSTER_SERVER}
  name: ${CLUSTER_NAME}
contexts:
- context:
    cluster: ${CLUSTER_NAME}
    namespace: ${NAMESPACE}
    user: ${USER_NAME}
  name: ${USER_NAME}-${CLUSTER_NAME}
current-context: ${USER_NAME}-${CLUSTER_NAME}
users:
- name: ${USER_NAME}
  user:
    client-certificate-data: $(cat "${USER_NAME}.crt" | base64 | tr -d '\n')
    client-key-data: $(cat "${USER_NAME}.key" | base64 | tr -d '\n')
EOF

# 9. Nettoyage des fichiers sensibles locaux (optionnel mais recommandé)
# On supprime le CSR Kubernetes pour ne pas encombrer le cluster
kubectl delete csr "${USER_NAME}-csr"

echo "=========================================================="
echo "🎉 Terminé avec succès !"
echo "📁 Les fichiers sont dans le dossier : ${USER_DIR}"
echo "📄 Transmettez ce fichier de configuration sécurisé à l'utilisateur :"
echo "   👉 ${USER_DIR}/${USER_NAME}-kubeconfig.yaml"
echo "=========================================================="
Utilisez le code avec précaution.

Comment utiliser ce script ?
    1. Sauvegardez le code dans un fichier nommé create-k8s-user.sh.
    2. Rendez le script exécutable :
       bash
       chmod +x create-k8s-user.sh
       Utilisez le code avec précaution.
    3. Exécutez le script en passant 3 paramètres : le nom de l'utilisateur, le namespace ciblé, et le rôle par défaut souhaité (ex: view, edit, admin).
       bash
       ./create-k8s-user.sh alice marketing edit
       Utilisez le code avec précaution.
Ce que fait ce script en arrière-plan :
    • Il crée un dossier local contenant les clés privées et publiques de l'utilisateur.
    • Il demande à Kubernetes de signer le certificat de l'utilisateur de manière native via l'API CertificateSigningRequest.
    • Il applique un RoleBinding dans le namespace désigné pour lier l'utilisateur à un rôle Kubernetes standard (view, edit, admin, ou cluster-admin).
    • Il isole toutes les données nécessaires (Certificat CA du cluster, certificat utilisateur, clé privée) dans un fichier kubeconfig unique et autonome pour l'utilisateur.

Voici un script Bash complet pour installer Kubernetes Dashboard, l'interface d'administration officielle de Kubernetes, accompagnée d'un utilisateur administrateur pour s'y connecter.
Script d'installation (install-dashboard.sh)
bash
#!/bin/bash

# Configuration des couleurs pour l'affichage
GREEN='\033[0;32m'
BLUE='\033[0;34m'
NC='\033[0m'

echo -e "${BLUE}==> Ajout du dépôt Helm de Kubernetes Dashboard...${NC}"
helm repo add kubernetes-dashboard https://github.io
helm repo update

echo -e "${BLUE}==> Installation de Kubernetes Dashboard via Helm...${NC}"
# Crée le namespace et installe le dashboard
helm upgrade --install kubernetes-dashboard kubernetes-dashboard/kubernetes-dashboard \
  --create-namespace \
  --namespace kubernetes-dashboard

echo -e "${BLUE}==> Création de l'utilisateur Administrateur (ServiceAccount)...${NC}"
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: ServiceAccount
metadata:
  name: admin-user
  namespace: kubernetes-dashboard
EOF

echo -e "${BLUE}==> Attribution des droits d'administrateur (ClusterRoleBinding)...${NC}"
cat <<EOF | kubectl apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: admin-user
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
- kind: ServiceAccount
  name: admin-user
  namespace: kubernetes-dashboard
EOF

echo -e "${BLUE}==> Génération du jeton (Token) de connexion...${NC}"
# Attente de quelques secondes pour s'assurer que les ressources sont prêtes
sleep 3
TOKEN=$(kubectl -n kubernetes-dashboard create token admin-user)

echo -e "${GREEN}================================================================${NC}"
echo -e "${GREEN}L'installation est terminée !${NC}"
echo -e "${GREEN}================================================================${NC}"
echo -e ""
echo -e "1. Pour accéder au Dashboard, lancez le proxy dans un terminal :"
echo -e "   ${BLUE}kubectl proxy${NC}"
echo -e ""
echo -e "2. Ouvrez ensuite votre navigateur à l'adresse suivante :"
echo -e "   http://localhost:8001/api/v1/namespaces/kubernetes-dashboard/services/https:kubernetes-dashboard-kong-proxy:443/proxy/"
echo -e ""
echo -e "3. Utilisez le jeton (Token) ci-dessous pour vous authentifier :"
echo -e "${BLUE}$TOKEN${NC}"
echo -e ""
Utilisez le code avec précaution.
Prérequis pour exécuter ce script
Avant de lancer le script, assurez-vous d'avoir :
    • Un cluster Kubernetes fonctionnel.
    • L'outil kubectl configuré avec les accès administrateur du cluster.
    • L'outil Helm installé sur votre machine.
Comment l'utiliser ?
    1. Créez un fichier nommé install-dashboard.sh et collez-y le code ci-dessus.
    2. Rendez le script exécutable :
       bash
       chmod +x install-dashboard.sh
       Utilisez le code avec précaution.
    3. Exécutez le script :
       bash
       ./install-dashboard.sh
       Utilisez le code avec précaution.
Souhaitez-vous plutôt configurer un accès externe permanent via un Ingress Controller (comme Nginx) ou préférez-vous utiliser une alternative au Dashboard officiel comme K9s (en ligne de commande) ou Lens ?

Voici un script Bash automatisé permettant de déployer Euro-Office Docs sur votre cluster Kubernetes en utilisant le dépôt Helm officiel fourni par le projet. [1]
Ce script installe les prérequis nécessaires (le provisionneur de stockage NFS, RabbitMQ, Redis et PostgreSQL) avant de déployer l'application principale Euro-Office Document Server. [1, 2]
Code du script d'installation (install-euro-office.sh)
bash
#!/bin/bash

# Arrête le script en cas d'erreur
set -e

echo "====================================================="
echo " Déploiement d'Euro-Office Docs sur Kubernetes"
echo "====================================================="

# 1. Ajout et mise à jour des dépôts Helm nécessaires
echo "--> Ajout des dépôts Helm..."
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo add nfs-server-provisioner https://kubernetes-sigs.github.io/nfs-ganesha-server-and-external-provisioner
helm repo update

# 2. Installation du provisionneur de stockage persistant (NFS)
# Remplacez standard par votre classe de stockage par défaut (ex: gp2, do-block-storage...)
echo "--> Installation du provisionneur de stockage persistant..."
helm install nfs-server nfs-server-provisioner/nfs-server-provisioner \
  --set persistence.enabled=true \
  --set persistence.storageClass="standard" \
  --set persistence.size="10Gi"

# 3. Déploiement de RabbitMQ
echo "--> Déploiement de RabbitMQ..."
helm install rabbitmq bitnami/rabbitmq \
  --set replicaCount=1 \
  --set auth.username=guest \
  --set auth.password=guest

# 4. Déploiement de Redis
echo "--> Déploiement de Redis..."
helm install redis bitnami/redis \
  --set master.persistence.enabled=false \
  --set replica.replicaCount=0

# 5. Déploiement de la base de données PostgreSQL
echo "--> Déploiement de PostgreSQL..."
helm install postgresql bitnami/postgresql \
  --set auth.username=postgres \
  --set auth.password=postgres \
  --set auth.database=postgres \
  --set primary.persistence.enabled=false

# 6. Récupération et configuration d'Euro-Office Docs
echo "--> Récupération des fichiers de configuration Euro-Office..."
if [ -d "Kubernetes-Docs" ]; then
  rm -rf Kubernetes-Docs
fi
git clone https://github.com
cd Kubernetes-Docs

# 7. Génération d'une clé JWT secrète pour la sécurité des échanges (ex: intégration Nextcloud)
JWT_SECRET=$(openssl rand -hex 32)
echo "--> Clé JWT générée pour Euro-Office : $JWT_SECRET"

# 8. Installation d'Euro-Office via Helm
echo "--> Déploiement de la release Euro-Office Docs..."
helm install euro-office . \
  --set connections.dbType=postgres \
  --set connections.dbHost=postgresql \
  --set connections.dbPort=5432 \
  --set connections.dbUser=postgres \
  --set connections.dbPassword=postgres \
  --set connections.dbName=postgres \
  --set connections.redisHost=redis-master \
  --set connections.rabbitmqHost=rabbitmq \
  --set jwt.secret=$JWT_SECRET \
  --set jwt.enabled=true

echo "====================================================="
echo " Déploiement terminé avec succès !"
echo " Note : Pensez à configurer un Ingress ou à exposer le"
echo " service Euro-Office pour y accéder à l'extérieur."
echo "====================================================="
Utilisez le code avec précaution.
Comment l'utiliser ?
    1. Assurez-vous d'avoir configuré l'accès à votre cluster avec kubectl et d'avoir installé Helm v3.
    2. Enregistrez le script ci-dessus sous le nom install-euro-office.sh.
    3. Rendez le script exécutable et lancez-le : [1]
       bash
       chmod +x install-euro-office.sh
       ./install-euro-office.sh
       Utilisez le code avec précaution.
Paramètres importants à adapter au besoin
    • Stockage (storageClass) : Dans l'étape du provisionneur NFS, remplacez "standard" par la StorageClass native de votre cloud provider (par exemple gp2 sur AWS EKS, ou microk8s-hostpath en local). [1]
    • Persistance des données : Pour des tests rapides, la persistance PostgreSQL et Redis a été désactivée (persistence.enabled=false). Pour un environnement de production, passez ces options à true et configurez des volumes adaptés.
